# moescope

Serve open Mixture-of-Experts (MoE) language models in expert-parallel (EP) form across several
GPUs, measure the GPU-to-GPU traffic of every MoE layer while the model runs, and estimate the
input topic and the generated tokens from that traffic alone.

In EP serving the experts of each MoE layer are spread over the GPUs. A router picks the top-k
experts for every token, the token is sent to the GPUs that hold those experts with an
`all_to_all`, the experts are computed there, and the results are sent back and combined. How many
rows go to each GPU depends on which experts were picked, and that depends on the input. moescope
runs this for real, records the per-layer, per-GPU row counts, and trains classifiers on them.

## What it does

- **EP serving.** One process per GPU. Experts are split in index order (`E/G` per GPU). The
  model produces the same output as when it runs on a single GPU.
- **Traffic measurement.** For every MoE layer, the number of rows actually sent to each GPU is
  recorded: per prompt in the prefill stage, per generated token in the decode stage. The traffic
  of a generated token is the traffic measured while that token is fed back into the model.
- **Feature extraction and classifiers.** The measured traffic is turned into classifier inputs
  (prefill traffic divided by the number of input tokens; decode traffic per generated token). An
  input-topic classifier and an output-token classifier (standardization followed by logistic
  regression) are trained and evaluated on them.

## Commands

| command | what it does |
|---|---|
| `moescope chat` | Loads the model in EP form, keeps it served, and reads prompts from an input line. Shows the response, the measured traffic per GPU, and the estimated topic and tokens. |
| `moescope collect` | Runs a file of prompts through EP serving and saves the measured traffic. |
| `moescope train` | Trains a classifier on saved traffic. |
| `moescope verify` | Installation check: `all_to_all` with random routing on CPU, measured counts against computed counts. |

## Install

```bash
git clone https://github.com/leehyeoklee/moescope.git
cd moescope
python3 -m venv .venv
source .venv/bin/activate          # Windows: .\.venv\Scripts\Activate.ps1
pip install -e ".[model,dev]"      # torch, transformers, accelerate, scikit-learn, pytest
moescope verify --gpus 4           # optional: a few seconds on CPU, ends with RESULT: PASS
```

`requirements-pinned.txt` lists the exact versions used for the results below.

## Usage

### A. Use the classifiers that ship with the repository

```bash
moescope chat --model olmoe --gpus 4
```

The model is loaded onto 4 GPUs and an input line appears. Type a prompt and press Enter; the
screen is redrawn after every generated token. When the response ends the input line comes back,
and the model stays loaded. An empty line, `exit` or Ctrl+D stops the serving processes. Every
prompt is handled as a separate request.

### B. Train classifiers on traffic measured on your own machine

```bash
# 1) collect: serve in EP form and save the measured traffic
moescope collect --model olmoe --task prefill --prompts examples/topic_prompts.json --gpus 4 --out traces/olmoe_prefill.npz
moescope collect --model olmoe --task decode  --prompts examples/prompts.json       --gpus 4 --out traces/olmoe_decode.npz

# 2) train: accuracy is printed, the classifier is saved under models/
moescope train --model olmoe --task domain --traces traces/olmoe_prefill.npz --gpus 4
moescope train --model olmoe --task output --traces traces/olmoe_decode.npz  --gpus 4

# 3) chat: classifiers found under models/ are used first
moescope chat --model olmoe --gpus 4
```

The prompt file is a JSON list of sentences. For the input-topic classifier each item carries its
label: `[{"text": "How much water should I drink?", "label": "Health"}, ...]`. The two example
files only show the format; training needs hundreds of prompts (the classifiers in the repository
used 1,000 labelled inputs and 300 chat prompts).

`collect` prints a report and ends with `RESULT: PASS` when the measured traffic of every layer
call equals the count computed from the routing (`layer_calls_mismatch: 0`). While it runs, every
process prints timestamped progress lines (`--quiet` turns them off):

```
[12:01:03 rank0] started on cuda:0 (NVIDIA L4), backend nccl, experts 0..15 of 64
[12:01:03 rank0] loading the checkpoint on CPU
[12:02:10 rank0] experts 0..15 on cuda:0, 5.1 GiB allocated
[12:03:40 rank0] all 4 processes ready, serving in EP form
[12:03:44 rank0] decode 1/30: 21 input tokens, 32 generated, 3.9s, traffic mismatches so far 0
```

### C. Traffic only

```bash
moescope chat --model olmoe --gpus 4 --no-clf
```

### Options of `chat`

| option | effect |
|---|---|
| (none) | input line; classifiers are looked up automatically |
| `--prompt "..."` | handle this prompt and exit (repeatable); `--prompts file.json` does the same for a file |
| `--output-clf`, `--domain-clf` | use these classifier files |
| `--no-clf` | no classifiers, response and traffic only |
| `--max-new-tokens N` | length of each response (default 48) |
| `--out file.npz` | save the measured traffic and generated tokens of the session |
| `--tiny` | small random model on CPU, no weights: checks the screen and the EP path |

Classifiers are looked up in this order: the files given as options, `models/<model>_g<gpus>_<task>.joblib`
(written by `moescope train`), then `moescope/pretrained/`. A classifier trained for a different
number of GPUs is rejected before the model is loaded.

## Classifiers in the repository

`moescope/pretrained/` holds an input-topic and an output-token classifier for each supported model
with 2 and 4 GPUs, so `chat` works right after installation. They were trained on the traffic of
1,000 topic-labelled inputs (10 topics, prefill) and 300 chat prompts (decode); the traffic was
computed from routing recorded on 2x Tesla T4, which equals the traffic measured in EP serving.
Accuracy on the held-out 20%:

| model | GPUs | input topic (10 classes) | output token |
|---|---|---|---|
| `olmoe` | 2 | 0.505 | 0.310 |
| `olmoe` | 4 | 0.580 | 0.392 |
| `granite` | 2 | 0.510 | 0.407 |
| `granite` | 4 | 0.550 | 0.455 |
| `qwen` | 2 | 0.415 | 0.341 |
| `qwen` | 4 | 0.440 | 0.428 |

`tools/build_pretrained.py` rebuilds them from the recorded routing. For another GPU count, or to
train on traffic measured on your own machine, follow usage B. The files are scikit-learn pickles
written with scikit-learn 1.6.1 (see `requirements-pinned.txt`).

## Checking EP serving against the unmodified model

With `--check`, `collect` first runs the same inputs with the unmodified model and adds to the report:

| field | stage | meaning |
|---|---|---|
| `token_agreement` | decode | share of freely generated tokens equal to the unmodified model |
| `forced_token_agreement` | decode | share of steps with the same next token when both are fed the same tokens |
| `forced_max_logit_diff` | decode | largest logit difference over those steps |
| `max_logit_diff` | prefill | largest logit difference at the last position |

For this comparison the unmodified model is spread over the available GPUs and uses per-expert
computation (`experts_implementation="eager"`), the same arithmetic as the EP path.

Results:

| model | hardware | processes | generated tokens equal | max logit difference | layer calls with traffic mismatch |
|---|---|---|---|---|---|
| OLMoE-1B-7B Instruct | 2× Tesla T4 (NCCL) | 2 (32 experts each) | 160 / 160 | 0 | 0 |
| Granite-3.0-3B-A800M | 2× Tesla T4 (NCCL) | 2 (20 experts each) | 160 / 160 | 0 | 0 |

Both runs used 5 prompts with 32 generated tokens each, plus a prefill run of the same prompts
(max logit difference 0). The CPU test suite repeats the same comparison on small randomly
initialized models with the OLMoE, Granite and Qwen1.5-MoE layouts, using 1, 2 and 4 processes.

## How prompts are fed to the model

- `chat` and `collect --task decode` wrap the prompt in the model's chat template. In `chat` the
  sentence itself is fed as a separate segment, so the input-topic estimate uses the traffic of
  the sentence only, as in training.
- `collect --task prefill` feeds the sentence alone, truncated to 32 tokens.
- `collect --raw` feeds the tokenizer's default encoding without the chat template.

## Output files of `collect`

| task | key | shape | content |
|---|---|---|---|
| `decode` | `tokens` | (N,) | generated token ids |
| | `routing` | (N, layers, k) | top-k expert ids of each generated token |
| | `measured` | (N, layers, G) | rows sent to each GPU while each generated token is processed |
| | `prefill_measured` | (P, layers, G) | rows sent to each GPU while reading each prompt |
| | `prompt_ids`, `step`, `generated` | | prompt index, step index, decoded text |
| `prefill` | `prefill_routing` | (tokens, layers, k) | top-k expert ids per input token |
| | `prefill_lengths` | (P,) | number of input tokens per prompt |
| | `prefill_measured` | (P, layers, G) | rows sent to each GPU per prompt |
| | `labels` | (P,) | topic labels, when the prompt file has them |

## Supported models and GPU counts

Checkpoints and revisions are pinned in `moescope/config.py`.

| `--model` | checkpoint | MoE layers | experts | top-k | usable `--gpus` |
|---|---|---|---|---|---|
| `olmoe` | allenai/OLMoE-1B-7B-0125-Instruct | 16 | 64 | 8 | 1, 2, 4, 8, 16, 32, 64 |
| `granite` | ibm-granite/granite-3.0-3b-a800m-instruct | 32 | 40 | 8 | 1, 2, 4, 5, 8, 10, 20, 40 |
| `qwen` | Qwen/Qwen1.5-MoE-A2.7B-Chat | 24 | 60 | 4 | 1, 2, 3, 4, 5, 6, 10, 12, 15, 20, 30, 60 |

`--gpus` must divide the number of experts and must not exceed the GPUs of the machine;
`collect` and `chat` stop before loading the model otherwise.

## Running on a multi-GPU instance

Example for a 4-GPU AWS instance (`g6.12xlarge`, 4× NVIDIA L4) with a PyTorch/CUDA image:

```bash
git clone https://github.com/leehyeoklee/moescope.git && cd moescope
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[model,dev]"
nvidia-smi --query-gpu=index,name,memory.total --format=csv     # expect 4 GPUs
pytest -q                                                        # CPU tests, including small EP-served models
moescope chat --model olmoe --gpus 4
```

Each process loads the checkpoint on CPU in turn and then moves its share to its GPU, so the host
needs about one model's worth of free RAM (about 14 GB for OLMoE in bfloat16).

## How it works

```
prompt ─▶ rank 0 (GPU 0): embeddings, attention, routers, experts 0 … E/G-1
             │
             │  every MoE layer:
             │    router picks top-k experts per token
             │    all_to_all dispatch ─▶ rank r (GPU r): experts r·E/G … (r+1)·E/G-1 compute
             │    all_to_all combine  ◀─ results, weighted sum on rank 0
             │    rows sent per destination GPU are recorded            ─▶ measured traffic
             ▼
        next layer … logits

measured traffic ─▶ traffic.measured_features / measured_prompt_features ─▶ classifiers
```

- `serve_ep` loads the model in every process, keeps only that process's experts on its GPU, and
  replaces the forward of the model's experts module with the EP path. Routers and all other
  computation are the model's own code.
- `ep.ep_layer` performs the `all_to_all` dispatch, the local expert computation and the combine
  for one MoE layer and returns the rows sent to each GPU. The same code runs under `NCCL` (GPU)
  and `gloo` (CPU). Half-precision hidden states are carried as bytes, and expert contributions
  are added in ascending expert order so the result equals the unmodified model.
- `placement.dest_counts_full` computes the same counts from the routing; every layer call is
  compared against it.
- `traffic` turns traffic into classifier inputs; `classifiers` trains and evaluates the
  input-topic and output-token classifiers (token dictionary = tokens seen at least 5 times in
  training).
- `chat` keeps the serving processes alive, passes each typed prompt to rank 0, and redraws the
  screen from the traffic measured for every generated token.
